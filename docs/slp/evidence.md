## Findings that changed code or the contract

- **A Lead that never mails the Supervisor leaves Human waiting.** The relayed brief reached the Lead, which analyzed the repository for four minutes, called codex-cli's native `send_message` toward `/root`, and ended its turn on the report in its own chat; the Supervisor never woke and Human saw nothing. The runtime now relays a supervised Lead's last message as `report` mail when the turn queued nothing to the Supervisor (`slp/reports.ts`); rerun on 2026-09-08 with the same brief, the report reached the Supervisor 3 minutes after the group started and the Supervisor answered Human. The same run showed the Lead still trying the native tool first under the "Paseo tools only" note, so the relay, not the prompt, is what carries the report; Disabling the feature was tried and reverted: with `features.multi_agent_v2 = { enabled: false }` and `features.multi_agent = false` in the thread's provider options (the record showed them), a new Supervisor listed `multi_agent_v1__*` in its catalog and `multi_agent_v1__spawn_agent` returned a fresh Codex agent (`nickname: "Meitner"`); `codex exec --disable multi_agent_v2 --disable multi_agent` on the CLI listed the same collaboration tools. Neither flag removes the tools on codex-cli 0.153.4, and v1 is the worse set because its spawn works, so members keep the host's Codex features.
- **Codex reaches for its own agent tools first.** With the address in its prompt, the same Supervisor first called codex-cli's native `send_message` with the Lead's id (`agent with id … not found`) and its native `list_agents` (which lists only Codex's own `/root`), then used Paseo's `send_agent_prompt`, which queued the mail and reached the Lead. The identity block now says the group is reachable only through Paseo's MCP tools and names the provider tools that know nothing about it. Separately, codex-cli 0.153.4 stamps some Paseo MCP requests with `MCP-Protocol-Version: 2026-07-28`, which SDK 1.29 answers with 400; the agent MCP route drops an unsupported version header before the transport sees it (`COMPAT(mcpProtocolHeader)`).
- **A Supervisor with no address for Lead does the work itself.** A user's supervised Codex group was asked in Vietnamese to analyze the project and propose an implementation plan; the Supervisor read the repository and wrote the plan, and an earlier `list_agents` had not shown it which agent was Lead. The role text said "relay to Lead" but named no route, and "answer from verified project information" read as licence to open the project. The identity block now carries the counterpart's agent id and the exact `send_agent_prompt` route, the Lead's id is planned at group creation so the Supervisor's prompt can name an agent that does not exist yet, and the role files define the method: what each role owns, what it never does, and the step order, with "any request needing project knowledge belongs to Lead" stated in the shared block.
- **The shared block first reads as reference material.** A user's supervised Codex group answered "I'm Codex" with no role, although its 11 KB role prompt was delivered: Codex places the composed text 17 KB into a developer message that opens with its own prompt and a competing "primary agent in a team" note, and the shared block began with "use this document only when Paseo assigns you a role", the assignment sitting at the end. The composed prompt now leads with an imperative identity block ("You are the Lead of a Paseo SLP group…") and the shared block states that the assignment has happened; the row above is from the rerun with that order.
- **Codex `never` also refuses MCP calls that would prompt.** The preparation policy took the readiness channel with it. Preparation now sets `default_tools_approval_mode: approve` on the Paseo server in the inner config; the daemon still refuses every Paseo tool but `slp_ready` per call. Whether a `full-access` source can call Paseo tools without that override was not isolated: the successor's `slp_checkpoint` succeeded on the same thread after the override had been sent at thread start.
- **Activation was not announced.** The runtime lifted the hold and pumped mail, but a successor with no queued mail heard nothing. Codex treated the next plain prompt as still pre-activation and refused to write; Claude did not. Completion now queues an `activation` mail that dispatches before anything else; the Codex row above is from the rerun with it.
- **An acknowledged cancellation at turn start does not stop Claude's first prompt.** A transfer requested while the Lead's first turn was still being admitted cancelled it after 41 ms; the CLI still answered `READY`, delivered as an autonomous turn after the manager had recorded the cancellation. The probe now waits for the run slot to flip before acting; the handoff contract already says not to trust the adapter's own interrupt, and this is why.
- **`ToolSearch` is refused during preparation.** Harmless: the direct MCP call worked. If a future Claude release needs `ToolSearch` to reach MCP tools, add it to the read allowlist.
- **A candidate told not to acknowledge still did.** The first restart attempt asked the Claude candidate to reply and wait; it called `slp_ready` anyway, so the stop landed after the switch and the second daemon rolled the `switched` transfer forward to `completed` with the successor active. That is the after-switch phase of gate 8, seen live by accident. The probe now stops as soon as the candidate record exists, which is the only stop point a model cannot move.
- **A stop can land before the candidate is stored.** The first Codex attempt stopped before the candidate's agent record was written; the abort retired the generation and had nothing to archive. The stray provider thread stays in the provider's own history. The rerun waited for the record and archived it.
- **Mail `accepted` precedes the run slot.** After activation the probe saw the successor idle and was refused with `busy`: acceptance is recorded at admission, before the provider reports the turn running, and the run slot clears after the idle event. Any caller sequencing turns behind SLP mail has to wait for the in-flight run to clear, not for the lifecycle alone.
